작성일: 2026년 11월 20일

상태: 구현 착수용 계획 완료. **Vercel + Supabase**를 필수 배포 구성으로 확정한다. 얼굴 자산과 신규 업무의 세부 내용은 구현 단계의 입력 항목이며, 이번 상태는 구현·배포 완료를 뜻하지 않는다.

## Vercel과 Supabase 배포 구성

```text
방문자 브라우저
  ├─ 3D · 스크롤 · 얼굴 반응 · 샘플 미니게임
  └─ Vercel의 Next.js 페이지와 API
       └─ 서버 전용 DB 연결 → Supabase PostgreSQL
                                └─ kyb_portfolio 스키마
정적 이미지 · 모델 · 영상 → 배포 자산
운영 중 업로드 기능 추가 시 → Supabase Storage 검토
```

Vercel은 기존 Next.js 앱을 배포하는 환경으로 사용한다. 서버 렌더링과 API를 포함하므로 정적 내보내기 전용 구성으로 바꾸지 않는다. DB 접근은 Node.js 서버 영역에서 수행하고 브라우저에 DB 자격증명을 전달하지 않는다. [Vercel Next.js 공식 문서](https://vercel.com/docs/frameworks/full-stack/nextjs)

기존 `postgres` 클라이언트를 사용하는 첫 구현안은 Supabase의 transaction pooler 연결을 기준으로 한다. `lib/content-store.ts`에는 `prepare: false`, `ssl: require`, `max: 3`이 이미 있다. 실제 연결 URL·동시 요청·유휴 후 재접속은 배포 환경에서 확인한다. 서버리스 인스턴스가 늘면 전체 연결 수도 늘기 때문에 인스턴스당 설정만으로 연결 안정성을 판단하지 않는다. [Supabase 연결 가이드](https://supabase.com/docs/guides/database/connecting-to-postgres)

현재 모듈 단위로 재사용하는 클라이언트의 유휴 연결을 Preview에서 점검한다. 연결이 멈추거나 타임아웃이 반복되면 Vercel 실행 방식과 풀 수명 관리를 검토하고, 필요 시 Supabase Data API 방식과 비교한다. 현재의 시간 제한 래퍼는 사용자 응답의 대기를 제한하는 코드이며 DB 쿼리를 실제 취소하는지 별도로 확인한다. [Supabase 서버리스 연결 문제 가이드](https://supabase.com/kb/troubleshooting/troubleshooting-connect_timeout-or-hanging-queries-in-vercel-serverless-functions-775f92)

### 환경 설정과 데이터 범위

- Vercel 프로젝트 루트는 저장소 루트, 빌드 명령은 기존 `npm run build`를 기준으로 한다. 현재 명령은 `next build --webpack`이다.
- `DATABASE_URL`과 `ADMIN_API_TOKEN`은 서버 전용 환경 변수로 관리한다. 기존 연결 URL이 비밀번호 플레이스홀더를 쓰는 경우에만 `SUPABASE_PASSWORD` 처리도 유지한다.
- 사이트 기준 주소는 `NEXT_PUBLIC_SITE_URL`과 기존 배포 URL 처리에 맞춰 canonical·공유 이미지 주소를 확인한다.
- Preview와 Production 환경 변수를 구분한다. Preview에서 쓰기 검수가 필요하면 분리된 Supabase 테스트 프로젝트를 사용한다. 운영 DB에 시험 데이터를 임의로 저장하지 않는다.
- 기존 `kyb_portfolio.posts`, `kyb_portfolio.projects`를 사용하며 첫 버전의 장면·얼굴 설정은 코드 데이터로 관리한다. 신규 테이블은 필수 요건이 아니다.
- DB 스키마 변경이 필요해지면 변경안을 별도로 검토한다. 빌드 시 migration을 자동 실행하지 않으며, 기존 공유 DB의 다른 스키마를 변경하지 않는다.
- 얼굴·모델은 사전 제작 자산으로 제공한다. 영구 파일을 Vercel 함수의 로컬 디스크에 저장하는 구조는 사용하지 않는다. 운영 업로드가 생기면 Supabase Storage 버킷과 접근 정책을 별도 설계한다.

### 배포 완료 판정

로컬 lint·typecheck·build 통과 후 Vercel Preview에서 다음을 확인한다.

1. 새로고침·상세 직접 접근·공유 주소·PDF·이미지·영상 경로 정상.
2. 3D·얼굴 반응·체험이 브라우저에서 작동하고 모바일·WebGL 대체 화면 정상.
3. Supabase 조회가 성공하는지 서버 응답으로 확인. 정적 폴백 표시만으로 DB 연결 성공을 판단하지 않음.
4. 인증 없는 쓰기 차단 및 분리된 테스트 DB에서 Studio 저장·수정·조회 확인.
5. 유휴 후 첫 요청·동시 조회·DB 실패 시 폴백과 오류 응답 확인.
6. 실제 배포의 자산 용량·함수 실행 시간·사용 플랜 제한을 확인하고 필요한 최적화 적용.

Production 배포 후에도 공개 화면과 실제 DB 조회를 다시 확인한다. 현재 문서 작업에서는 배포 설정 변경·환경 변수 등록·DB 접속·배포를 수행하지 않았다.

## 기술 제안

현재 React 19 구성에는 Three.js와 React Three Fiber 9 계열을 우선 후보로 둔다. 공식 문서는 Fiber 9와 React 19의 대응을 명시한다. 실제 설치 버전은 구현 시 호환성을 다시 확인해 잠금 파일로 고정한다. [React Three Fiber 공식 문서](https://r3f.docs.pmnd.rs/getting-started/introduction)

스크롤 연출은 GSAP ScrollTrigger의 진행률 연동과 고정 구간 기능을 후보로 둔다. 장면과 본문의 타이밍을 하나의 타임라인에서 관리하며 별도의 부드러운 스크롤 라이브러리는 초기 범위에 추가하지 않는다. [ScrollTrigger 공식 문서](https://gsap.com/docs/v3/Plugins/ScrollTrigger/)

CSS Modules와 기존 아이콘·타이포그래피 구조를 활용한다. 3D가 담당하는 부분은 공간과 오브젝트다. 제목·본문·링크·체험 컨트롤은 의미 있는 HTML로 제공한다. 데이터 조회와 비밀값을 클라이언트 장면 코드에 포함하지 않는다.

## 제안 파일 구성

다음은 새 파일의 제안이며 아직 생성한 구현 파일은 아니다.

```text
components/experience/
  experience-shell.tsx       장면 로딩과 정적 대체 화면
  experience-canvas.tsx      단일 캔버스와 카메라
  scroll-story.tsx           HTML 섹션과 진행률 연결
  scene-objects.tsx          데이터·검증·제품 오브젝트
  report-check-demo.tsx      샘플 검증 체험
  current-work.tsx           최근 업무 영역
  experience.module.css     경험 화면 스타일
data/
  experience.ts             대표 사례 ID·장면 순서·현재 업무 선정
  experience-demo.ts         공개용 샘플 데이터와 판정 기준
public/experience/
  ...                       최적화된 자산과 정적 대체 이미지
```

기존 조회 결과를 기준으로 대표 ID에 해당하는 사례를 찾아 장면에 전달한다. 이미 존재하는 프로젝트 제목·기간·상태를 경험 설정에 복사해 별도로 관리하지 않는다. 대표 사례가 없는 경우 해당 장면을 숨기거나 일반 목록으로 연결한다.

DB 프로젝트와 정적 사례를 합치는 규칙, 동일 ID 처리, 상세 페이지 폴백을 구현 전에 확인한다. 첫 버전의 장면 설정과 최근 업무 선정은 코드 데이터로 관리해 DB 마이그레이션 없이 진행한다. Studio에서 장면까지 편집하려면 타입·검증·API·저장을 함께 설계하는 별도 단계가 필요하다.

## 장면과 상태 설계

홈 본문은 6개 섹션으로 구성하고 단일 캔버스가 각 구간을 시각화한다. 스크롤 진행률이 카메라 위치·오브젝트 변형·텍스트 강조를 결정한다. 매 프레임 React 전체를 다시 그리는 대신 장면 내부 참조를 갱신하는 구조를 검토한다.

동작 시나리오는 다음과 같다.

- 첫 진입: 이름·소개·바로가기를 먼저 노출하고 캔버스는 준비되면 활성화.
- 로딩 실패·WebGL 미지원: 정적 이미지와 동일 HTML 본문 사용.
- 역방향·빠른 스크롤: 진행률에 맞는 상태로 직접 계산해 이벤트 누적 방지.
- 창 크기 변경: 섹션 높이와 카메라 구도를 다시 계산.
- 상세 방문 후 복귀: 기존 읽기 위치 복원 여부 확인.
- 체험 진입: 본문 위치 유지, 닫을 때 진입 버튼으로 초점 복귀.
- 움직임 감소: 큰 이동·회전을 생략하고 모든 내용을 일반 흐름으로 제공.
- 탭 비활성화·캔버스 비노출: 불필요한 렌더링 정지.

샘플 검증 체험은 `준비 → 문장 선택 → 근거 확인 → 검증 결과`의 상태를 갖는다. 초기화는 첫 상태로 돌아가며, 어느 상태에서나 사례 설명으로 이동할 수 있다. 미선택 시 검증을 누르면 선택 안내를 보여준다. 체험 결과는 실제 운영 서비스의 정확도나 검증 성능 수치로 사용하지 않는다.

## 본인 얼굴 인터랙션 추가 계획

첫 화면에 본인 얼굴이 포인터 방향을 바라보는 연출을 추가한다. 우선 방향별 이미지를 사용하는 방식을 제안하며, 실제 얼굴 원본과 표현 취향을 확인한 후 확정한다. 기존 프로젝트 자산 목록에서는 전용 초상 원본을 식별하지 못했다.

1. 원본 확보: 사용할 정면·측면 사진의 위치와 허용 범위 확인.
2. 방향 자산 준비: 동일 구도·조명·크기의 정면·좌·우 및 필요 시 위·아래 이미지. 생성 방식이면 눈·코·얼굴 윤곽·헤어의 일관성을 사용자와 검토.
3. 인터랙션 시제품: 얼굴 영역 기준 포인터 위치를 방향으로 매핑. 중앙의 작은 움직임에는 정면 유지, 방향 경계에는 여유 구간을 두어 반복 전환 방지.
4. 전환 검수: 짧은 페이드와 즉시 교체를 비교해 눈·얼굴이 겹쳐 보이지 않는 방식 선택. 기울기는 보조 효과로만 사용.
5. 스크롤 연결: 입장 구간에서 다음 사례 방향으로 시선 이동. 해당 구간을 벗어나면 업데이트 중지.
6. 대체 동작: 터치에서는 탭·장면 전환, 움직임 감소에서는 정면, 이미지 실패에서는 정적 대체 화면 사용.

제안 파일은 `components/experience/interactive-portrait.tsx`와 `public/experience/portrait/`다. 방향 이미지 중 정면을 우선 로딩하고 나머지는 입장 구간에서 준비한다. 대체 텍스트는 인물 소개로 유지하고 장식적 시선 변경마다 스크린 리더 알림을 발생시키지 않는다.

검수는 정면 복귀, 빠른 왕복 이동, 방향 경계, 포인터 이탈, 리사이즈, 터치, 키보드 탐색 방해 여부, 움직임 감소, 이미지 실패, 스크롤과 시선 제어 충돌을 포함한다. 본문·버튼 위로 얼굴이 겹치거나 시선을 따라 페이지가 움직이지 않아야 한다.

연속적인 고개 회전과 표정이 필수라면 3D 모델·텍스처·리깅을 별도 제작 단계로 추가한다. 단일 사진의 CSS 회전만으로 실제 옆얼굴이 보이는 연출을 구현했다고 간주하지 않는다.

## 자산 계획

실제 이미지·영상 자산이 이미 있어 이를 프로젝트의 정체성을 보여주는 소재로 활용한다. Amazon·Bid Master·별자리의 화면을 먼저 검토하고 공개 범위와 해상도를 확인한다. 대형 장식 모델을 먼저 제작하기보다 간단한 패널과 흐름 오브젝트로 장면을 검증한 후 조명·재질을 다듬는다.

첫 버전 필수 자산은 메인 오브젝트, 대표 사례 화면, 정적 대체 이미지, 샘플 데이터 표다. 기존 동영상은 재생 요청 시 로딩하는 방식을 검토한다. 오디오와 대량 이미지 프레임 시퀀스는 초기 필수 자산이 아니다.

성능의 내부 목표는 PC 60fps·모바일 30fps 이상이며 검증된 결과가 아니다. 대표 기기·브라우저·측정 구간을 기록하고 낮은 성능에서는 해상도·그림자·후처리를 줄인다. 첫 화면의 내용을 읽기 위해 3D 다운로드가 완료될 때까지 기다리게 하지 않는다.

프로젝트에 정의된 `npm run lint`, `npm run typecheck`, `npm run build`를 실행한다. 자동 테스트는 샘플 검증 규칙, 체험 상태, 데이터 연결처럼 회귀 가능성이 있는 동작에 집중한다. 화면의 완성도는 실제 브라우저에서 별도로 확인한다.

## 콘텐츠 정합성과 후속 확인

구현 전에 Amazon 검증 관련 표현을 통일하고, README의 홈 설명을 실제 구성에 맞춘다. `/portfolio`의 경력과 앞으로 추가할 업무의 소속·기간·개인 기여를 확인한다. `SiteHeader`의 `/#work`, `/#about`을 사용한다면 새 홈에 해당 섹션 ID를 제공한다.

현재 업무의 범위는 아직 확정되지 않았다. 작업 공간에 존재한다는 이유만으로 사용자 개인 실적이나 공개 가능한 자료로 등록하지 않는다. 실제 내용이 정리되면 기획서의 ‘지금 만드는 것’과 프로젝트 데이터에 반영한다.

완료 기준은 첫 화면에서 정체성을 이해하고, 대표 사례를 경험하고, 모든 사례의 본문을 일반 탐색으로 읽으며, 새 업무를 메인 장면 재작업 없이 추가할 수 있는 상태다. 배포는 구현·로컬 검수와 구분해 기존 저장소 운영 규칙을 확인한 뒤 진행한다.
