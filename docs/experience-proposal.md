# 강연배 포트폴리오 인터랙티브 경험 기획서

작성일: 2026년 11월 20일

상태: 구현 착수용 기획 완료. 필수 운영 환경은 **Vercel 배포와 Supabase DB**다. 얼굴 원본과 추가할 업무의 상세 내용은 제작 단계에서 보충한다. 구현·배포 검증 완료를 뜻하지 않는다.

**추천 컨셉은 스크롤로 들어가는 AI 제품 실험실이다.** 방문자가 데이터를 움직이고, 잘못된 결과를 발견하고, 업무가 자동화되는 과정을 체험한다. 기존 포트폴리오의 핵심인 ‘사용자 문제에서 운영되는 제품까지’를 화면 전체의 이야기로 확장한다.

## 현재 포트폴리오에서 발견한 강점

복제된 저장소의 콘텐츠와 코드를 기준으로 검토했다. 실행 화면, 운영 서비스, DB 원자료를 검증한 결과는 아니다. 성과 수치는 저장소의 서술과 출처 시점을 함께 사용하고, 현재 수치로 재해석하지 않는다.

현재 홈은 `app/page.tsx`의 제목·빠른 링크와 검색·필터 가능한 프로젝트 아카이브다. 정적 프로젝트는 19개이며 실무 11개, 개인 제품 4개, Lab 2개, 학생 프로젝트 2개로 구성돼 있다. DB 프로젝트는 별도로 합쳐지므로 실제 운영 목록 수는 다를 수 있다.

깊이 있는 내용은 이미 충분하다. 특히 다음 세 사례에는 문제·판단·장애·협업·성과가 정리돼 있다.

| 사례 | 콘텐츠에서 드러나는 강점 | 인터랙션으로 전달할 핵심 |
| --- | --- | --- |
| Amazon Ads Reporting Agent | LLM 생성과 Python 검증 분리, 원본 수치 대조, 운영 중 실패의 재발 방지 | 그럴듯한 문장을 신뢰할 수 있는 리포트로 만드는 과정 |
| Bid Master | 수집·비정형 문서 해석·품목 정규화·사용자 판단 연결 | 흩어진 업무가 한 흐름으로 정리되는 변화 |
| Byeoljari.com | 도메인 계산과 AI 해석 분리, 결제 검증·멱등성·결과 전달 | 사용자가 끝까지 결과를 받도록 설계하는 완결성 |

Local Browser Agent, BigQuery AI Analyst, MeetSub, Exam Forge에도 체험에 적합한 소재가 있다. 이처럼 서로 다른 제품을 묶는 정체성은 ‘AI를 실제 사용자와 운영 환경에 연결하는 엔지니어’다. 기존 메타데이터의 AI Product Engineer와도 맞는다.

현재 아카이브는 많은 프로젝트를 찾아보기 좋지만, 첫 방문자가 위 강점을 순서대로 체감하도록 이끄는 장치는 약하다. 따라서 홈은 대표 사례를 경험하는 공간으로 바꾸고, 전체 목록과 상세 설명은 기존 경로에서 계속 확장한다.

## 전체 경험의 방향

방문자는 스크롤로 실험실 안을 이동한다. 장면 속 데이터 조각이 정리되고, 검증 장치를 통과하고, 실제 제품 화면으로 완성된다. 이동 중에는 핵심 문장이 읽히고, 관심 있는 장면에서는 버튼을 눌러 짧게 체험한다.

입체감은 진한 잉크색 공간, 부드러운 조명, 떠 있는 얇은 패널로 만든다. 기존 보라색 강조를 계승하되 텍스트 구역은 밝고 안정적인 면으로 처리한다. 제안 색상은 잉크 `#101426`, 페이퍼 `#F5F3EF`, 바이올렛 `#6557FF`, 보조 민트 `#6ED7B2`이며 대비는 구현 시 검증한다. 한글 본문은 읽기 쉬운 고딕, 짧은 상태 표시와 숫자만 고정폭 글꼴을 사용한다.

대표 장면의 스크롤과 확대·분해·조립을 주요 연출로 삼고, 선택적 체험을 더한다. 캐릭터 자유 이동은 후속 후보로 둔다. 여러 프로젝트의 의미를 전달하는 데 필요한 조작부터 만든다.

## 장면별 구성

| 장면 | 화면과 조작 | 메시지와 연결 |
| --- | --- | --- |
| 1. 입장 | 이름과 소개 뒤로 프로젝트 패널들이 떠 있다. 첫 스크롤에 카메라가 중앙으로 접근한다. | ‘사용자 문제에서 운영되는 제품까지.’ 대표 사례·전체 목록·PDF 바로가기 |
| 2. 데이터가 리포트가 되다 | 데이터 조각이 생성 → 검증 → 교정 → 최종 검증을 통과한다. 오류 수치 하나가 검증 구간에서 멈춘다. | Amazon Ads의 생성과 검증 분리. ‘오류 찾아보기’ 체험과 상세 링크 |
| 3. 반복 업무가 연결되다 | 흩어진 입찰 문서가 구조화되고 품목·지역·비교 화면으로 정렬된다. | Bid Master의 업무 개선. 서술된 3~4시간 → 30분은 회의록 기준임을 함께 표시 |
| 4. 제품이 사용자에게 도착하다 | 작은 별빛이 입력 → 계산 → 해석 → 전달 경로를 따라간다. 마지막에 실제 서비스 화면이 열린다. | Byeoljari의 결과 전달 중심 설계. 결제·복구 흐름의 샘플 설명 |
| 5. 실험실이 확장되다 | 카메라가 물러나 여러 제품 패널이 보인다. 관심 분야나 프로젝트를 탭한다. | MeetSub·Exam Forge·Dubby·Lab과 추가할 현재 업무 |
| 6. 사람에게 돌아오다 | 장면의 움직임이 잦아들고 경력·일하는 방식·연락처가 나타난다. | 개인 기여, 협업 방식, GitHub·PDF·연락 |

장면 2~4에는 항상 ‘사례 자세히 보기’를 둔다. 핵심 텍스트는 캔버스 밖의 HTML로 제공한다. 방문자가 멈추면 글을 읽을 수 있고, 역방향 스크롤에서는 장면도 돌아간다. 자동 재생을 기다려야 다음으로 갈 수 있는 구간은 만들지 않는다.

메인 이야기의 대표 사례는 세 개로 제한하고, 새 업무는 목록과 ‘지금 만드는 것’에 추가한다. 새 사례를 대표로 선정할 때만 메인 장면을 교체한다.

## 반응하는 본인 초상

사용자가 추가로 요청한 연출은 본인의 얼굴이 좌우를 보거나 움직이는 인터랙션이다. 첫 화면에 본인 초상을 배치해 방문자의 움직임에 반응하고, 첫 스크롤에서 시선을 대표 프로젝트 방향으로 돌리도록 제안한다. 얼굴은 방문자를 맞이하고 프로젝트로 관심을 이어주는 역할을 맡는다.

| 표현 방식 | 보이는 효과 | 준비할 자료와 특징 |
| --- | --- | --- |
| 사진 기울기와 깊이 효과 | 사진과 배경이 포인터에 따라 조금씩 이동·기울어짐 | 정면 사진으로 시작 가능. 실제 눈동자나 옆얼굴 회전과는 다른 효과 |
| 방향별 얼굴 이미지 | 정면·좌·우·위·아래 시선이 포인터 방향에 따라 전환 | 같은 구도·조명의 방향별 사진 또는 본인 사진 기반 제작 이미지 필요. 본인 닮음과 전환 자연스러움 검수 |
| 본인 기반 3D 아바타 | 머리와 눈이 부드럽게 회전하고 표정 변화 가능 | 얼굴 모델·텍스처·리깅과 기준 사진 필요. 제작·용량·렌더링 범위가 커짐 |

첫 버전은 **본인 모습을 유지한 방향별 초상**을 추천한다. 좌우 시선은 실제 방향별 이미지로 표현하고, 얕은 기울기 효과를 더해 입체감을 준다. 연속적인 얼굴 회전이 꼭 필요하면 3D 아바타로 확장한다. 실제 사진과 스타일화된 아바타 중 어느 표현을 쓸지는 사용자 초상 자료와 선호를 확인한 뒤 정한다.

PC에서는 얼굴 영역 가까이의 포인터에만 반응하고, 포인터가 멀어지면 정면으로 돌아온다. 첫 스크롤에서 얼굴이 다음 장면을 바라본 뒤 작아지거나 사라지면서 프로젝트가 중심이 된다. 모바일에서는 첫 진입·탭·장면 전환으로 반응하게 하고 카메라나 기기 센서 접근은 요구하지 않는다.

빠른 마우스 움직임에는 완만하게 반응하고, 얼굴 방향이 경계에서 깜빡이지 않도록 전환 기준을 둔다. 움직임 감소 설정에서는 정면 사진을 유지한다. 초상이 로딩되지 않아도 이름·소개·프로젝트 링크는 바로 보여야 한다.

현재 확인한 프로젝트 자산 목록에서는 전용 얼굴 원본을 식별하지 못했다. 제작 전에 사용할 사진의 위치와 사용 범위를 확인한다. 초상 연출은 첫 버전의 추가 요구로 포함하되, 원본 확보 전에는 정적 자리와 인터랙션 구조까지 준비한다. 현재 문서는 계획이며 얼굴 이미지나 모델을 생성한 상태는 아니다.

## 첫 체험은 리포트 검증 게임

Amazon Ads 사례의 설계 판단을 짧은 미니게임으로 경험하게 한다. ‘AI가 만든 문장에서 원본과 다른 숫자를 찾아보세요’라는 안내와 함께 샘플 데이터 표와 리포트 세 문장을 보여준다.

1. 방문자가 의심되는 문장을 선택한다. 터치와 키보드로 모두 선택할 수 있다.
2. 원본 표의 해당 값과 문장의 값이 나란히 강조된다.
3. ‘검증 실행’을 누르면 샘플 비교 규칙에 따라 불일치가 표시된다.
4. 생성과 검증을 분리한 실제 설계와 사례 상세로 연결한다.

전체 체험은 15~30초를 목표로 하며 타이머나 점수 경쟁은 두지 않는다. 정답과 무관하게 설명을 볼 수 있고 초기화·건너뛰기를 제공한다. 실제 광고 데이터나 외부 LLM 호출 없이 미리 정한 샘플로 동작하며, 실제 검증기의 모든 동작을 재현한다고 표현하지 않는다.

후속 체험 후보는 Bid Master의 품목 매칭, Local Browser Agent의 선택 실패와 폴백, MeetSub의 부분 자막과 최종 번역 비교다. 모두 같은 난이도와 조작 규칙으로 묶을 필요는 없으며 사례의 핵심 판단을 드러내는 것을 우선한다.

## 현재 업무를 추가하는 방식

기존 19개 프로젝트와 현재 추가할 업무를 같은 목록에 수용한다. 업무는 부서별 페이지 수가 아니라 해결한 사용자 문제와 사용 흐름을 기준으로 묶는다.

작업 공간 메모리에 있는 후보는 교육·운영 관리, 캠프 콘텐츠 운영, 마케팅 콘텐츠·성과 관리, AI 업무 지원이다. 아직 이번 포트폴리오의 확정 실적이 아니므로 사용자의 담당 범위와 공개 가능한 결과를 확인한 후 등록한다.

각 사례에는 대상 사용자, 문제, 담당 역할, 설계 판단, 실제 사용 화면, 확인된 결과, 진행 상태, 최근 갱신일을 기록한다. 운영·진행·완료·프로토타입은 기존 상태값을 활용한다. 성과는 숫자가 없어도 운영 피드백, 지원 범위, 실패 처리, 이전과 달라진 작업 흐름으로 설명할 수 있다.

현재 업무를 추가해도 나머지 3D 장면을 수정할 필요가 없어야 한다. 목록과 상세에 기본 등록하고, 체험이나 대표 장면은 선택 사항으로 둔다. ‘지금 만드는 것’은 날짜 문자열의 ‘현재’를 검색해 자동 추정하지 않고 별도 선정 목록과 갱신일을 사용한다.

## 탐색과 화면 크기 대응

상단에 대표 사례·전체 프로젝트·소개·PDF·연락 경로를 제공한다. ‘전체 프로젝트’는 언제든 `/projects`로 이동한다. 일반 탐색과 체험 탐색에 동일한 사례 주소를 사용해 이력서와 공유 링크에서도 접근할 수 있게 한다.

PC에서는 입체 장면 옆에 본문을 배치하고 모바일에서는 짧은 장면과 본문을 세로로 이어 놓는다. 모바일 조작을 캐릭터 이동이나 마우스 호버에 의존시키지 않는다. 화면이 작거나 성능이 낮으면 오브젝트 수·해상도·그림자를 줄인다.

움직임 감소 설정과 WebGL 미지원 환경에서는 정적 장면과 일반 본문을 제공한다. 스크린 리더와 키보드로도 프로젝트·체험 설명·연락처에 접근할 수 있어야 한다. 음성이나 배경음은 기본 경험에 포함하지 않는다.

## 첫 버전과 이후 확장

첫 버전은 입장 장면, 세 대표 사례의 스크롤 연출, 리포트 검증 체험 한 개, 현재 업무 영역, 전체 목록·상세 연결, 모바일·정적 대체 화면까지다. 기존 영상은 실제 서비스의 증거로 상세에 활용하고, 새 홈의 스크롤 진행을 영상 재생 시각에만 의존시키지 않는다.

이후에는 추가 업무의 대표 사례화, 두 번째 체험, 선택적 자유 탐험 순으로 확장한다. 첫 시제품은 입장과 Amazon Ads 장면까지 만들고, ‘예쁘다’뿐 아니라 ‘어떤 강점을 가진 사람인지 이해했는가’를 확인한다.

## 콘텐츠 정리 과제

Amazon 사례는 `case-studies.ts`에서 Python 검증을 명시하지만 `projects.ts`와 `project-challenges.ts`에는 검수 Agent라는 표현이 있어 LLM 검수로 읽힐 여지가 있다. 새 체험과 기존 설명을 함께 정리해야 한다.

README의 홈 소개 구성은 현재 `app/page.tsx`와 다르다. 경력에는 `2025.07 — 현재 Hurdlers`가 기록되어 있으므로 신규 업무 추가 시 소속·기간·병행 여부를 확인한다. 성과 수치와 날짜, 개발 기간과 운영 기간도 각각 구분해 원문 기준을 유지한다.

## 확정 운영 조건

Next.js 사이트와 서버 API는 Vercel에서 운영하고, 프로젝트·글 등 동적 콘텐츠는 기존 Supabase PostgreSQL의 `kyb_portfolio` 스키마를 사용한다. 브라우저에서 3D·스크롤·얼굴·미니게임을 실행하는 구조로 설계한다. 방문할 때마다 서버에서 얼굴 영상이나 3D 모델을 생성하지 않는다.

첫 버전의 초상·모델·이미지는 미리 제작해 정적 자산으로 배포한다. 운영 중 업로드가 필요해지면 Supabase Storage를 별도로 연결한다. DB 사용이 Storage·Auth 도입까지 의미하는 것은 아니며, 현재 Studio 인증은 기존 방식을 유지한다.

기획 범위는 확정됐으며 남은 제작 입력은 얼굴 사진·표현 스타일, 추가 업무별 담당 범위와 공개 자료다. 공개 준비 완료는 Vercel Preview에서 화면·API·Supabase 실제 연결까지 검수한 시점으로 정의한다.
